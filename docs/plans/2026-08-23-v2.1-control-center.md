# Assignmark 2.1 Reliability and Control Center Implementation Plan

> **For Hermes:** Implement this plan task-by-task with strict RED → GREEN → REFACTOR cycles and a fresh independent review after the final edit.

**Goal:** Ship a calendar-only v2.1 control center without allowing multi-tab storage races, resolver scans, filters, or destructive controls to erase valid checkoffs.

**Architecture:** Move aggregate-data mutations into one MV3 service-worker coordinator so all Schoology tabs share one serialized read-modify-write queue. Content scripts become clients that receive validated snapshots and react to `chrome.storage.onChanged`; the worker receives legacy userscript data during first initialization because page `localStorage` is unavailable in the extension worker. Introduce a calendar adapter and rendered-item registry so v2.1 remains calendar-only while later Schoology surfaces can be added without broadening the existing calendar resolver.

**Tech Stack:** Manifest V3, JavaScript ES modules bundled by esbuild, `chrome.runtime` messaging, `chrome.storage.local`, Node test runner, jsdom, Chromium/CDP HTTPS fixture verification.

---

## Non-negotiable invariants

- Keep the only named permission as `storage` and the only host match as `https://fuhsd.schoology.com/*`.
- Add no network calls, analytics, remote executable code, credentials, or broad host permissions.
- Preserve v1.2 import keys and never delete legacy page data automatically.
- Preserve existing canonical IDs, fallback IDs, aliases, timestamps, and sibling/path-shift regression behavior.
- Only explicit uncheck, scoped clear, or separately confirmed clear-all operations may remove checked state.
- `filter` is the sole visibility authority in v2.1; legacy `hide` remains stored only for rollback compatibility.
- Progress and clear-view scope use unique resolved IDs from the entire rendered calendar view, independent of the active filter.
- Version 2.1 adds no non-calendar Schoology selectors.

## Release blockers this revision closes

1. Two tabs can currently overwrite each other because each writes a stale whole-object snapshot.
2. `clearStates(null)` conflates scoped and global destruction.
3. Every resolver call writes storage even when nothing changes.
4. Legacy `hide` and the new filter can both hide items, making All ineffective.
5. Calendar DOM discovery and control-center scope lack explicit adapter/registry seams.
6. The built v2.1 extension has not yet passed a clean-profile runtime probe.

### Task 2: Add a serialized mutation coordinator

**Objective:** Ensure independent tabs cannot overwrite one another.

**Files:**
- Refactor: `src/core.js`
- Create: `src/background.js`
- Create: `src/storage-client.js`
- Modify: `manifest.json`
- Modify: `scripts/build.mjs`
- Test: `test/core.test.js`
- Create: `test/storage-client.test.js`

**RED tests:**
- Two independent clients checking different IDs leave both persisted.
- A clear in one client cannot erase an unrelated newer check from another.
- Failed persistence leaves the coordinator snapshot unchanged.
- Initialization imports legacy data only when extension data is absent.

**Implementation:**
- Extract `DataRepository`, the authoritative aggregate-data owner, from `ExtensionStore`.
- Every repository mutation reloads the latest persisted value inside one worker-local queue, applies one mutation, writes only if changed, and updates memory only after success.
- `src/background.js` owns one repository and handles explicit message operations.
- `StorageClient` sends messages, validates returned snapshots, and exposes the current read-only snapshot to content code.
- Content initialization passes parsed legacy values; the worker ignores them when extension data already exists.
- Add `background.service_worker` to Chrome MV3 manifest. No new permission.
- Bundle `src/background.js` separately into `dist/background.js`.

**Commands:**
```bash
node --test --test-name-pattern='independent clients|coordinator|failed persistence' test/core.test.js test/storage-client.test.js
npm test
npm run build
```

**Expected:** focused RED before implementation, then all tests pass; built manifest references local `dist/background.js`.

**Commit:** `fix: coordinate checkoff storage across tabs`

### Task 3: Make resolution pure, batched, and write-free when unchanged

**Objective:** Stop polling and rerenders from causing repeated storage writes.

**Files:**
- Modify: `src/core.js`
- Modify: `src/background.js`
- Modify: `src/storage-client.js`
- Test: `test/core.test.js`

**RED tests:**
- Resolving identical candidates twice causes zero writes on the second call.
- Resolving multiple items in one scan causes at most one write.
- A fully unchanged batch causes no write.
- Fallback-to-canonical reconciliation still keeps the newest timestamp.

**Implementation:**
- Export pure `resolveCandidates(data, candidates)` returning `{ resolution, changed }`.
- Add repository `resolveMany(candidateList)` and commit once only when any result changes aliases/state.
- Content injection consumes one batch result per scan rather than calling storage once per node.

**Commit:** `fix: batch id reconciliation without no-op writes`

### Task 4: Separate scoped and global destructive capabilities

**Objective:** Make accidental global deletion impossible through an omitted argument.

**Files:**
- Modify: `src/core.js`
- Modify: `src/background.js`
- Modify: `src/storage-client.js`
- Test: `test/core.test.js`

**RED tests:**
- `clearCompleted([])` is a no-op and performs zero writes.
- `clearCompleted(ids)` removes only checked IDs in the explicit scope and returns exact timestamps.
- `clearAllStates()` is separately named and returns the exact global snapshot.
- Undo uses `Math.max(existing, removed)` and cannot overwrite a newer timestamp.
- Undo remains correct when a fallback ID reconciles to canonical between clear and restore.

**Implementation:**
- Remove nullable/no-argument clear semantics.
- Add `clearCompleted(ids)`, `clearAllStates()`, and `restoreStates(snapshot)` as separate coordinator operations.
- Global clear remains reachable only from the distinctly labeled UI action and exact-count confirmation.

**Commit:** `fix: separate scoped and global clearing`

### Task 7: Integrate the control center through the client and registry

**Objective:** Wire progress, filters, clear, and undo without giving UI code direct storage access.

**Files:**
- Modify: `src/content.js`
- Modify: `src/control-center.js`
- Modify: `src/content.css`
- Modify: `test/control-center.test.js`
- Create: `test/content-integration.test.js`

**RED tests:**
- Repeated scans produce one control center and one checkbox per logical calendar item.
- Check/uncheck immediately refreshes progress and filtering.
- Progress is invariant across All/Pending/Done.
- Clear View scopes to checked unique IDs in the entire registry, not visible-filter matches.
- Clear View confirmation reports the exact count.
- Clear All is separately labeled and exact-count confirmed.
- Cancel changes nothing.
- Undo is one-level, restores UI/state, and is replaced only by a later destructive action.
- A storage-change notification refreshes stale tab UI.
- SPA removal recreates the control center.

**Implementation:**
- Content script uses `StorageClient`, `CalendarAdapter`, and `RenderedItemRegistry`.
- Batch-resolve one scan, inject controls, populate registry, then render once.
- Subscribe to `chrome.storage.onChanged` and refresh client snapshot/UI.
- Use `filter` only for visibility; use `dim` only for presentation.
- Minimum practical 44px controls, visible focus, `aria-live`, reduced motion, and width containment at 390px.

**Commit:** `feat: integrate reliable Assignmark control center`

## Final acceptance gate

- Two independently initialized tabs cannot lose each other’s checks.
- Clear/undo cannot overwrite an unrelated newer mutation.
- Repeated unchanged resolution performs zero writes; one scan performs at most one reconciliation write.
- Scoped and global clear are different APIs and differently confirmed UI actions.
- Existing v1.2/v2.0 states, timestamps, aliases, canonical IDs, fallback IDs, and `dim` survive upgrade.
- All shows all rendered calendar records; Pending and Done affect visibility only.
- Progress and scope deduplicate IDs and do not change merely because a filter is active.
- No new named permission, host, network transmission, remote code, or credential handling.
- Full tests, audit, build, ZIP, static compliance checks, two-tab Chromium probe, responsive/accessibility checks, and final independent review pass.
